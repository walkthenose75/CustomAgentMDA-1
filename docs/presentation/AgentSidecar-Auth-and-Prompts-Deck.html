Making the Sidecar agent feel like part of Dynamics

Two enhancements: keep the agent authenticated for the whole Dynamics session, and surface the right prompts for the form the user is on — grounded in the actual runtime code.

Issue · Auth times out mid-session Question · Form-specific prompts Identity · Stays delegated
Executive summary

What we're solving, in one glance

The problem today

  • Users sign into Dynamics 365 Sales / Service / Field Service, open the sidecar, and must authenticate again to the agent.
  • That agent token expires mid-session (~60–90 min) while the Dynamics session lives on — so the chat breaks and they re-auth.
  • Prompts are generic — no guidance tailored to the Opportunity, Case, or work order they're looking at.

The outcome

  • Invisible after a one-time consent. Silent refresh keeps the agent alive; worst case one silent re-auth per day.
  • No lost conversations. Token renews behind the scenes; a graceful "Reconnect" chip replaces dead panes.
  • Right prompts, right form, right role. A Sales Manager on an Opportunity sees different suggestions than an AE.

Design principle preserved: the agent keeps answering as the signed-in user, so knowledge stays gated by each person's own permissions. We do not trade that away for convenience.

Issue #1 · Root cause

The token is captured once — and never refreshed

Your acquireToken() already does silent-first (good). The real bug is in renderConversation(): the access token is snapshotted at render time, handed to the client as a static string, and nothing renews it.

// model-driven/webresources/maftagsc_/copilot/agentSidePane.ts
const client = new CopilotStudioClient(settings, token); // token captured ONCE
...
activeToken = token;                                     // static string, never refreshed

When the ~60–90 min Entra access token expires, the live conversation's calls start returning 401 and the user is forced to sign in again — the mismatch against the much longer Dynamics session is exactly the bad UX you described.

Issue #1 · Solution

Four layers that make re-auth (almost) disappear

Core Silent refresh loop

Capture expiresOn, refresh ~5 min early via acquireTokenSilent. MSAL renews through the cached rotating refresh token over a CORS POST — no popup, no iframe, no third-party cookies. The conversation never dies.

Invisible Shared Entra SSO

Pass the Dynamics UPN as loginHint and try ssoSilent first. After the one-time consent, the token is obtained with zero UI, riding the existing Entra session.

Admin Align with Entra CA

Put the SPA app under the same Conditional Access sign-in frequency + persistent browser session as Dynamics so they expire together. SPA refresh tokens cap at 24h → at most one re-auth/day.

UX Graceful reconnect

If interaction is ever truly required, show an inline "Session expired — Reconnect" chip that resumes the same conversation — instead of a blank pane.

Issue #1 · The honest constraints

"Can we authenticate programmatically?" — yes, via silent SSO

Why not literally reuse Dynamics' creds

Dynamics never exposes its Entra access token to page script, and there's no supported API to mint a CopilotStudio.Copilots.Invoke token from Xrm. "Programmatic auth" in practice = silent SSO against the shared Entra session — which is exactly what ssoSilent does.

The tempting shortcut to avoid

Your repo still ships a disabled DirectLine token broker. A server-minted bot token would make auth fully invisible — but the agent would answer as a service identity, not the user, breaking per-user knowledge security. Keep delegated.

Net result: from "re-auth mid-session" → invisible after a one-time consent, with at most one silent-or-single-click re-auth per 24 hours.

Question #2 · You already have the hook

Form-aware prompts, using context you already send

The runtime already resolves the current table via getEntityBinding(configuration, context.entityName), and the context envelope + pvaSetContext already carry entityName, recordName, and CurrentUserRoles to the agent. Adding prompts is an extension, not a rebuild.

// sidecarConfiguration.ts — the perfect extension point
export interface SidecarEntityBinding {
    logicalName: string;
    screenName: string;
    prompts?: { label: string; text: string; roles?: string[] }[]; // ← add
}
Question #2 · Three ways, by who owns the list

Config-driven now, agent-driven documented

Option A

Config-driven role-aware chips in the web resource. Deterministic, admin-managed, filtered by the roles you already compute. Chosen for v1.

Option B

Agent-driven via a Copilot Studio topic that branches on entityName and returns Suggested Actions / Adaptive Card. Managed in Studio. Documented as an option.

Option C

Generative — ask the agent to propose 4 things it can help with for this form/role. Most dynamic, least governable. Future enhancement.

Role-aware in action: on the Opportunity form a Sales Manager sees "Summarize deal risk / Coach the rep," while an AE sees "Draft next steps / Who are the stakeholders?" — same form, different chips.

Guardrails & next step

What we will not break

Preserved by design

  • Keep the localStorage sign-in handshake — no acquireTokenPopup / redirect-bridge (COOP).
  • Keep delegated identity — no token broker revival.
  • src/generated read-only · HashRouter · Fluent UI v9 · DataverseFieldLabel for new fields.
  • No Dataverse schema change for v1 — JSON-blob persistence.

One risk we de-risk early

Whether the Copilot Studio SDK can swap the token without resetting Web Chat — verified first thing in Phase 2, with reconnect-by-conversationId as the fallback.

Out of scope here: deploying to an environment (live form mutations) and any schema provisioning — both gated on the plugins + a dev environment + your approval.
