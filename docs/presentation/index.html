Silent Auth Continuity &
Dynamic Role-Aware Prompts

Two production-grade enhancements to the Agent Sidecar — the Copilot Studio agent embedded in Dynamics 365 model-driven forms. One keeps the conversation alive for the length of a real work session; the other makes the agent context-aware on every form.

Status Live in Contoso-Dev PR #3 · MERGEABLE · 17 commits Schema change None required Identity Delegated (per-user)
01 — Executive summary

What we built, and why it matters

The Agent Sidecar surfaces a Copilot Studio agent in a side pane on Dynamics 365 forms, authenticated as the signed-in user (delegated identity) so its answers respect that user's permissions. Two gaps limited it in the field. We closed both — with no Dataverse schema change, no new interactive sign-in surface, and the delegated-identity model fully preserved.

Feature 1

Silent auth continuity

Problem: the delegated access token was captured once at pane load and never refreshed. Around the 60–90 minute mark the token expired, the agent started returning 401s mid-session, and the user was forced to re-authenticate.

Solution: a proactive silent-refresh loop that renews the token ~5 minutes before expiry over a CORS call, hot-swaps it into the live conversation without losing the transcript, retries transient failures, and falls back to a one-click "Reconnect" chip only when a real interactive re-auth is unavoidable.

Feature 2

Dynamic role-aware prompts

Problem: the pane offered no starting points, or generic ones. Users stared at an empty box and didn't know what the agent could do for this record.

Solution: form-specific suggested-prompt chips, keyed by the table's logical name and filtered by the user's security roles. Clicking a chip sends its text with full record/form context attached. Prompts ship as a bundled catalog and can be overridden per-table from an in-app admin editor — all persisted as JSON on an existing column.

02 — System architecture

Where the sidecar lives

The pane is a web resource (agentSidePane.js) hosted in an iframe on the model-driven form. It signs the user in with MSAL.js against Microsoft Entra ID, then talks to the Copilot Studio agent through the CopilotStudioClient / DirectLine connection rendered by Web Chat. Per-environment behaviour (which agent, which tables, which prompts) is read at runtime from a Dataverse configuration record.

Non-negotiable constraints preserved

Identity & sign-in

  • Delegated identity — the agent answers as the signed-in user; the disabled DirectLine token-broker (service identity) is not revived.
  • localStorage sign-in handshake retained; no acquireTokenPopup or redirect-bridge (Dynamics COOP breaks those).
  • Refresh uses a CORS POST against the rotating refresh token — not a hidden iframe, so third-party-cookie policies don't break it.

Code & data

  • No Dataverse schema change for v1 — the prompt catalog is a JSON blob on an existing text column.
  • Code App rules honoured: src/generated/** read-only, three-layer architecture, HashRouter, Fluent UI v9.
  • Green baseline stays green: typecheck, unit tests, lint, build, plus the model-driven build + node tests.
03 — Feature 1

Silent auth continuity

A Dynamics user often keeps one record open for hours. The original pane captured the delegated token exactly once, in renderConversation() (new CopilotStudioClient(settings, token)), and never renewed it. When Entra expired that token the live conversation had no way to present a valid one — every subsequent turn 401'd, and the only escape was a full re-auth that also wiped the transcript.

Root cause

Access tokens are short-lived by design (~60–90 min). A single capture guarantees expiry inside a normal work session. The fix is not a longer token — it's a loop that renews ahead of expiry and swaps the fresh token into the running conversation without disturbing it.

The refresh lifecycle

On every successful token acquisition the pane arms a one-shot timer for expiresOn − 5 min (clamped to a 30 s floor). When it fires, the pane silently re-acquires the token, ends the old DirectLine connection, and re-renders Web Chat reusing the existing store — so the transcript and conversationId survive the swap — then schedules the next refresh against the new expiry.

Acquisition ladder & failure handling

Token acquisition tries the quietest path first and only escalates when it must. Background refreshes distinguish a transient failure (retry, the current token is still valid through the skew window) from a genuine interaction-required failure (surface a one-click Reconnect).

SSO hinting keeps re-auth invisible

The launcher captures the Dynamics UPN (Xrm.Utility.getGlobalContext().userSettings.userName) into shared localStorage. The pane passes it as MSAL loginHint and tries ssoSilent before any interactive prompt — so even the "Reconnect" path is typically a single click with no credential entry, courtesy of the existing Entra session.

Key code

Pure timing math — import-free and unit-tested in isolation (tokenRefresh.ts):

// Refresh 5 min ahead; never schedule tighter than a 30 s floor.
export const TOKEN_REFRESH_SKEW_MS = 5 * 60 * 1000;
export const MIN_TOKEN_REFRESH_DELAY_MS = 30 * 1000;

export function computeRefreshDelayMs(
    expiresOn: Date | null | undefined, now: number,
    skewMs = TOKEN_REFRESH_SKEW_MS, minDelayMs = MIN_TOKEN_REFRESH_DELAY_MS
): number | null {
    if (!(expiresOn instanceof Date)) return null;   // unknown lifetime → reactive only
    const expiresAt = expiresOn.getTime();
    if (!Number.isFinite(expiresAt)) return null;
    return Math.max(expiresAt - skewMs - now, minDelayMs);
}

Renew & hot-swap without losing the transcript — the heart of the loop (agentSidePane.ts):

async function refreshActiveToken(configuration) {
    const acquired = await acquireToken(false, configuration, activeLoginHint);
    if (!acquired) { showReconnect(); return; }   // interaction genuinely required

    activeToken = acquired.accessToken;
    activeExpiresOn = acquired.expiresOn;
    activeConnection?.end();                         // tear down old DirectLine
    resetWebChatHost();
    renderConversation(acquired.accessToken,
        resolveContext(activeContext, configuration),
        configuration, activeStore ?? undefined);    // ← reuse store = transcript survives
    scheduleTokenRefresh(configuration);             // re-arm against the new expiry
}

The catch around this call retries a transient failure up to MAX_SILENT_REFRESH_RETRIES = 3 at 60 s intervals before showing the reconnect chip; the SDK has no token-setter, so rebuilding the client on the same conversationId while passing the existing store is the sanctioned swap.

04 — Feature 2

Dynamic role-aware prompts

The pane already knew the current table's logical name and the user's roles — it just wasn't using them. We turned that context into a bar of suggested-prompt chips above the Web Chat input. Each chip is scoped to a table and, optionally, to specific security roles; clicking one sends its text through the same wrapped postActivity the free-text box uses, so the full record and form context rides along automatically.

The prompt pipeline

Prompts come from two sources that merge deterministically. A bundled catalog (promptCatalog.ts) compiled into the pane guarantees prompts appear in every deployment with zero configuration. An optional authored JSON blob on the config record (edited from the admin app) overrides the catalog per-table. applyPromptCatalog() only backfills bindings that don't already declare their own prompts — so authored prompts always win.

Why no schema change

The bundled catalog means prompts work the moment the pane loads — even against a Dataverse config whose binding table carries no prompts column. The authored override is a compact JSON string on an existing memo column. A dedicated table can come later; it isn't needed to ship.

Key code

Deterministic merge — pure, never mutates input (promptCatalog.ts):

// Fill each binding that lacks its own prompts with the catalog entry.
// Binding-level (authored) prompts take precedence; catalog closes the gap.
export function applyPromptCatalog(configuration, catalog = SIDECAR_PROMPT_CATALOG) {
    const entityBindings = {};
    for (const [key, binding] of Object.entries(configuration.entityBindings)) {
        const hasOwnPrompts = Array.isArray(binding.prompts) && binding.prompts.length > 0;
        const catalogPrompts = catalog[key];
        entityBindings[key] = (!hasOwnPrompts && catalogPrompts?.length)
            ? { ...binding, prompts: catalogPrompts }   // backfill only
            : binding;                                  // authored wins untouched
    }
    return { ...configuration, entityBindings };
}

One serialization boundary — the admin app and runtime agree on shape & caps via src/lib/sidecar-prompts.ts:

Everything is already built, tested, and packaged as PR #3 against the upstream repo. Because it started from Marty's repository, the exact path depends on whether the customer cloned or forked it — and who holds merge rights upstream. In all cases the work is review-and-merge, not re-implementation.

If they forked Marty's repo

  1. The branch feature/auth-refresh-and-dynamic-prompts already lives on the fork and drives PR #3.
  2. In VS Code: git fetch, check out the branch, open the GitHub Pull Requests extension, and review PR #3 inline.
  3. Merge into their main (squash recommended to collapse 17 commits), or forward PR #3 to Marty if upstream is the destination.

  1. Add the fork as a remote and pull the branch:

To ship without waiting on upstream, merge into the fork's main and deploy from there — the same line already proven in Contoso-Dev.

Testing & verification

npm run typecheck && npm test && npm run lint && npm run build

Silent-auth test recipe (four layers)

1 · Unit

npm run test:model-driven exercises computeRefreshDelayMs (skew/floor math) and the loginHint / ssoSilent plumbing.

2 · Observe the real refresh

Open a record form, DevTools → Network, watch the silent …/oauth2/v2.0/token POST fire ~5 min before expiresOn; the chat never blinks.

3 · Force a fast refresh

Temporarily raise TOKEN_REFRESH_SKEW_MS above the token lifetime → computeRefreshDelayMs clamps to the 30 s floor, so a refresh fires within ~30 s. Confirm the chat survives on the same conversationId. Revert the skew after.

4 · Force reconnect

Make acquireTokenSilent throw InteractionRequiredAuthError (sign out in another tab / clear the MSAL cache entry); the inline "Reconnect" chip must resume the same thread. Transient failures retry 3× at 60 s first.

Prompt smoke test

  • Open an contoso_incidentreport record → the incident chips render above the input.
  • Click one → it dispatches with record context and the agent answers about that incident.
  • Sign in as a user missing a gated role → role-scoped chips are hidden.
  • Author a prompt override on the config record → it replaces the bundled catalog for that table.
